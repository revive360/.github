# CI: build once, keep the bill in view

Let the apps share the toolchain. Start with the limits, keep runs focused and retain the build evidence.

Checked against official GitHub documentation on **2026-11-25**. These are published limits, not a read of Revive360's account/billing dashboard. Recheck before enabling paid capacity.

## Published allowances

| Resource | Public repositories | Private repositories / org allowance |
| --- | --- | --- |
| Standard hosted Actions compute | Free independently of the monthly compute allowance; larger runners are billed. | Free for organizations currently includes **US$12/month of compute**, shared with eligible cloud sandbox usage, not a fixed minutes quota. |
| Concurrent standard hosted jobs | **20** for Free across the account/org, including at most **5 macOS** jobs. | Same plan-wide concurrency; not 20 per repository. |
| Job duration | Hosted job maximum **6 hours**; workflow total up to **35 days**, including waiting/approval. | Same hosted limits. |
| Actions artifacts | Free plan table includes **500 MB**; do not assume public compute means unlimited artifact storage. | **500 MB**, shared with applicable Packages storage; hourly storage accrual. |
| Cache | Default **10 GB per repo**, independent of artifacts; default eviction after **7 days without access**, oldest entries evicted at capacity. | Same default. Optional paid cache expansion is not part of this zero-spend design. |
| Artifact/log retention | Default 90 days, configurable **1–90 days**. | Default 90, configurable **1–400 days**, subject to org policy. |
| Packages | Public packages free. | Free org includes **500 MB storage / 1 GB monthly transfer**; applicable storage shared with Actions artifacts. |
| GHCR | Container registry image storage/bandwidth **currently free**; policy can change. | Same current GHCR policy. |
| Release assets | Up to **1,000 assets/release**, each **under 2 GiB**; no total release-size/bandwidth quota stated. | Use Releases for distributable binaries, not long-lived Actions artifacts. |

Sources: [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), [included plan usage](https://docs.github.com/en/billing/reference/product-usage-included), [Actions limits](https://docs.github.com/en/actions/reference/limits), [cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), [retention settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), [Packages billing](https://docs.github.com/en/billing/concepts/product-billing/github-packages), [release quotas](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

Older guides quote 2,000 private minutes for Free. The current official allowance is monetary; runner rate and other eligible usage determine the actual minutes. Public standard hosted compute does not draw from it. Treat the billing dashboard as the operational authority when the owner configures the account.

## Proposed architecture

1. **Devkit owns the toolchain image** `ghcr.io/revive360/devkit`. Build GCC/newlib/xsdk and pinned libraries once when compiler recipes, `upstreams.lock.json` or the image definition change, not in every app run. The image includes licenses, corresponding source/patches or compliant source availability, lock manifest and provenance. Preserve GPL obligations for redistributed compiler components. Publish a version tag plus immutable digest; apps use `ghcr.io/revive360/devkit@sha256:<approved-digest>`.
2. Build the image on a disposable hosted Linux runner with a measured timeout below six hours. If cold GCC cannot finish, split compiler/runtime/library stages into independently verified image layers and jobs; reuse pinned output by digest. Never silently substitute a developer's compiler. Sign/attest the image and record the approved digest before app workflows can use it. No image was built or published in R2; this is the proposed rollout.
3. App PRs touching relevant source/build/dependency paths run one Linux job and only necessary native/cross targets, no default Windows/macOS matrix. Tags `v*` trigger full release builds from reviewed main commits. For required checks, prefer an always-starting lightweight gate that detects relevant paths and explicitly reports a no-build-needed result: event-level path filters can leave required checks pending forever. Cancel superseded PR runs, never an active release. Limit matrix parallelism to 2 and compilation to `-j2` initially.
4. Cache pip/downloads and app object files keyed by OS, architecture, toolchain **digest**, lock hash and build flags. Cache misses must work; caches are disposable and repo-scoped, not the shared compiler distribution. Fork PRs can read accessible base caches: never cache secrets. Do not promote untrusted fork-produced output or cache content into a release.
5. Project tags start an automated build/test/checksum/attestation/draft flow. After a maintainer records that **the exact CI artifact hash** passed real-console testing, the final publish job verifies evidence, source/tag and hash, attaches licenses, source, `SHA256SUMS` and signed provenance, then publishes assets to Releases. Console validation is a human gate, not a claim inferred from CI. No locally built binary may be substituted after validation. Prefer draft/tag preparation that permits this gate without overwriting public tags.
6. Separate read-only PR jobs from release jobs. Default `permissions: contents: read`; release-only job gets `contents: write`, attestation job gets `id-token: write` and `attestations: write`, image publisher alone gets `packages: write`. Full-SHA pins for third-party Actions and immutable container digests. No secrets/privileged `pull_request_target` execution of fork code. **No self-hosted runners for public repos**: fork PR code can compromise the host and later jobs. See [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use).
7. Catalog CI validates schema/semantic rules, runs negative tests and renders records/SVGs, checks committed outputs against a fixed reference date and also builds with today's date to reveal expiry. It uploads a short-lived review artifact only; it never publishes Pages, pushes generated code or issues certificates. The owner must deploy status changes. GitHub artifact attestations are available for **public** Free repositories; private attestations require Enterprise Cloud. [Attestation availability](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations).

## At the limit and plan B

Concurrency exhaustion queues work; job/workflow time limits terminate work. Cache capacity evicts entries and can cause thrashing; it must not affect correctness. Reduce invalidation breadth and remove dead cache keys. Artifact uploads fail when storage is exhausted; shorten transient retention to 3–7 days, delete stale artifacts/caches as appropriate and move public releases to Releases. Deletion does not undo already accrued storage charges.

Without a valid payment method, metered use beyond the allowance is blocked; with payment enabled, overage can be billed unless a budget stops usage. Set a **zero additional-spend budget with stop usage enabled** for Actions/Packages where supported, enable usage alerts and inspect billing regularly. [Budget controls](https://docs.github.com/en/billing/how-tos/set-up-budgets) and [Packages behavior](https://docs.github.com/en/packages/learn-github-packages/introduction-to-github-packages).

First reduce private runs, matrices, redundant builds and retention; keep legitimate open-source work public on standard hosted runners. Ask support about concurrency where warranted; buy Team or metered capacity only after a separate owner decision. If hosted compute is temporarily unavailable, pause releases and continue local development/verification, clearly labeled development artifacts. Local builds do **not** become trusted Project releases. A future isolated private builder would need its own reviewed threat model, provenance and policy change; it is not authorization to attach a self-hosted runner to a public repo. GHCR pricing changes require rechecking budget and choosing another verified OCI distribution service or reducing image retention before enabling charges.
